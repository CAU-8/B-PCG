# 방법 비교: 기존 지형 생성 방법론과 B-PCG

기존 지형 생성 방법을 B-PCG 와 같은 격자·같은 시드로 돌려, 같은 지표로 재고 같은 방식으로 그려 비교하는 도구입니다. 방법 목록은 Galin 외 2019 "A Review of Digital Terrain Modeling"(*Computer Graphics Forum* 38(2), doi 10.1111/cgf.13657)의 분류와 그림 34 의 대표 방법을 따릅니다. 방법마다 지형을 만드는 **연산 과정**(중간 지도, 반복마다 바뀐 값)도 남겨 화면에서 한 장씩 봅니다.

계산·지표·그림은 C# 라이브러리(`src/Bpcg/Compare/`)와 콘솔(`bpcg compare`, `src/Bpcg.Cli/CompareCommand.cs`)이 합니다. 스튜디오(`src/bpcg_studio/compare_api.py`)는 결과 파일을 읽고 콘솔을 부릅니다.

## 1. 한 장 요약

```sh
uv run bpcg compare run                       # configs/compare/default.toml → out/compare/default
uv run bpcg compare list --set default        # 시드끼리 묶어 지표 표 (--json 이면 JSON)
uv run bpcg compare render --set default --seed 0 --method bpcg   # 고도 그림 한 장 (--stage i 는 과정 단계)
uv run bpcg compare methods                   # 방법과 매개변수 목록 (--json 이면 JSON)
uv run bpcg studio                            # 위 막대 '방법 비교' → /compare 화면
```

`uv run bpcg compare …` 는 C# 콘솔을 (바뀐 것만) 빌드한 뒤 그대로 넘깁니다. 빌드해 둔 콘솔을 바로 부를 때는 `dotnet src/Bpcg.Cli/bin/Release/net10.0/Bpcg.Cli.dll compare …` 입니다.

- **같은 격자.** 모든 방법이 같은 n×n 평면 격자(기본 256×256, 칸 50 m, 한 변 12.8 km)에 고도를 냅니다.
- **같은 시드끼리 묶기.** 결과는 `out/compare/<이름>/seed_NNNN/<방법>/` 에 쌓이고, 화면과 표는 시드마다 모든 방법을 한 묶음으로 보여 줍니다.
- **같은 잣대.** 지표는 모든 고도에 같은 코드로 잽니다. 물길은 네 가장자리를 출구로 둔 같은 격자의 D8 로 다시 계산합니다.
- **같은 그림.** 고도 그림은 같은 빛(북서 315°, 고도각 45°), 같은 과장(1배), 같은 색표로 그립니다. 그림은 한 번에 한 장씩만 그립니다.
- **연산 과정.** 방법마다 3~12 장의 중간 지도와, 반복마다 바뀐 값의 곡선을 남깁니다.

기본 설정(시드 3개 × 방법 12개, 256²)은 노트북(M 계열, 병렬)에서 약 12 초에 돕니다. 대부분은 `stream_power`(시드마다 약 2 초)입니다.

## 2. 비교하는 방법

| id | 계열 | Galin 2019 | 화면에서 보이는 것 | B-PCG 와 다른 점 |
|---|---|---|---|---|
| `fbm` | 절차적 | 3.1.3 | 여러 크기의 노이즈를 더한 언덕. 어디나 비슷한 거칠기 | 원인이 없음, 물길이 이어지지 않음 |
| `ridged` (+ `ridged_sharp`) | 절차적 | 3.1.3, 그림 7·8 | 노이즈를 뒤집어 만든 날카로운 산마루 | 위와 같음 |
| `multifractal` | 절차적 | 3.1.3 | 낮은 곳은 매끈한 평야, 높은 곳은 거친 산 | 위와 같음 |
| `warped` | 절차적 | 3.1.3, 그림 8 | 좌표를 비틀어 흐르는 듯한 무늬 | 침식 흉내일 뿐 물질 이동이 없음 |
| `diamond_square` | 절차적 | 3.1.1, 그림 5 | 반씩 나눈 격자의 흔적(사각 무늬, 첫 나눔 자리의 극값) | 위와 같음 |
| `faulting` | 절차적 | 3.1.2, 그림 6 | 직선 단층마다 한쪽이 솟은 계단 | 위와 같음 |
| `thermal` | 시뮬레이션 | 4.1 | fbm 을 안식각보다 가파른 비탈만 무너뜨림 | 노이즈 지형을 꾸미는 후처리 |
| `hydraulic` | 시뮬레이션 | 4.3.2 | fbm 에 물방울 입자를 굴려 깎고 쌓음(게임에서 흔함) | 위와 같음, 융기 없음 |
| `stream_power` | 시뮬레이션 | 4.2.1, 그림 20 | 융기 + 하천 침식을 수백만 년 시간 적분 | 가장 가까운 기존 방법. 암석 하나, 땅속 없음, 정상상태를 바로 풀지 않음 |
| `quilting` | 예제 기반 | 5.1, 그림 26·27 | 실제 DEM(가봉 로페 30 m) 조각을 이어 붙임 | 국소는 진짜, 물길은 이어진다는 보장 없음 |
| `bpcg` | 우리 | — | 평면 히어로: 융기 단면 → 층 경계별 정상상태 → 물·흙·지하수·동굴 | — |

- **절차적 방법의 높이.** 높이 단위가 없으므로 `grid.relief_m`(기본 1,500 m)에 맞춥니다.
- **침식 방법의 시작 지형.** `thermal`·`hydraulic` 의 시작 지형은 같은 시드의 `fbm` 과 같습니다. 그래서 묶음 안에서 침식 전후를 바로 비교할 수 있습니다.
- **`stream_power` 의 조건.** 기본값은 B-PCG 평면 히어로와 같은 융기 단면(북쪽 산맥)과 출구(남쪽 가운데 5칸)입니다. 그래서 같은 조건에서 '시간 적분 대 정상상태'를 비교합니다.
- **넣지 않은 방법.** 논문의 신경망(5.3)과 희소 모델(5.4)은 학습 자료와 가중치가 필요해 넣지 않았습니다. 설계도가 신경망을 쓰지 않기로 한 것과도 맞습니다. 격자 유체 기반 수력 침식(4.3.1)과 지형 스케치 방식(3.2)은 4장의 방법으로 더할 수 있습니다.

## 3. 결과 폴더와 같은 시드 묶음

```text
out/compare/<이름>/
  compare.json                    설정 전체(격자, 시드, 방법과 매개변수), 지표 설명, 고친 때, 코드 판
  seed_0000/<id>/z.npy            고도 (n, n) float32 [m]
                 meta.json        방법, 매개변수, 시드, 시간, 캐시 키, 고도 범위, 진단값
                 metrics.json     지표
                 layers/*.npy     덧붙인 지도 (B-PCG 의 지하수면·강·지표 암석 등)
                 stages/NN.npy    연산 과정 중간 지도, stages.json 에 이름·종류·설명·범례
                 trace.json       반복마다 바뀐 값(곡선)과 단계별 값(막대)
                 *.png            그림 (필요할 때 한 장씩 만듦)
```

- **결정성.** 무작위 값은 모두 정수 해시(`Bpcg.Core.Hashing`)로 만들어, 같은 (격자, 시드, 매개변수)면 늘 같은 고도가 나옵니다. 과정 기록을 켜도 고도는 비트까지 같습니다(`tests/Bpcg.Tests/CompareTool`).
- **캐시.** 매개변수·격자·시드·기록 여부·코드 판이 같으면 다시 만들지 않습니다. 코드 판은 `Bpcg` 어셈블리의 모듈 ID 입니다. 빌드가 결정적이라 소스가 같으면 같고, 라이브러리 어디든 고치면 모든 방법을 다시 만듭니다(보수적). `--force` 는 늘 다시 만듭니다.
- **지표 입력.** 지표는 저장한 float32 고도로 잽니다. 그래서 새로 만들 때와 캐시로 읽을 때 지표가 같습니다.
- **시간.** `meta.json` 의 `seconds` 는 과정 기록에 든 시간을 뺀 생성 시간입니다. `wall_seconds` 는 기록을 포함한 시간입니다. 프로세스에서 방법을 처음 쓸 때 32×32 로 한 번 미리 돌려, 첫 실행(JIT) 시간이 섞이지 않게 합니다.
- **격자 고정.** 한 묶음 폴더는 격자 하나만 받습니다. 격자를 바꾸면 `--out` 을 바꿉니다.
- **Python 판과 같음.** C# 으로 옮기기 전 Python 판(numba)과 n = 64·96, 시드 0·7 에서 12 개 방법의 고도와 연산 과정 지도가 비트 단위로 같음을 확인했습니다(2026-10-08). 옮기면서 고친 것은 두 가지입니다. 스펙트럼 β 는 rfft 반쪽 평면을 numpy 전체 평면 평균과 같게 셉니다. 지표는 float32 고도로 잽니다(Python 판은 새로 만들 때 float64 로 재서, 웅덩이 점 수가 캐시와 달랐음).

## 4. 방법 추가와 수정

**매개변수만 바꾼 변형**은 설정 TOML 에 줄을 더합니다. 코드는 고치지 않습니다.

```toml
[[methods]]
id = "fbm_rough"          # 결과 폴더 이름 (소문자·숫자·_·-)
method = "fbm"            # 등록된 방법 (bpcg compare methods)
params = { gain = 0.7, octaves = 10 }
```

명령줄에서 한 번만 바꿀 때는 `--param fbm.octaves=6`, `--param grid.n=128`, `--param run.snapshots=false` 를 씁니다.

**새 방법**은 `src/Bpcg/Compare/` 에 C# 파일을 하나 만들고 `MethodRegistry.Builtins()` 에 한 줄을 더합니다. 저장소 밖 파일을 읽는 플러그인은 없습니다(Python 판의 `[plugins]` 는 옮기지 않음).

```csharp
using Bpcg.Core;

namespace Bpcg.Compare;

/// <summary>대조군: 칸마다 독립인 무작위 높이를 이웃 평균으로 다듬습니다.</summary>
public static class WhiteNoiseMethod
{
    private const long Stream = NoiseMethods.StreamBase + 901; // 다른 방법과 겹치지 않는 해시 용도 번호

    public static readonly CompareMethod WhiteNoise = new(
        "white_noise",
        "흰 노이즈",
        "procedural", // procedural | simulation | example | ours
        "대조군",
        "칸마다 독립인 무작위 높이",
        [new Param("smooth", 0L, "이웃 평균을 몇 번", Kind: "int", Lo: 0, Hi: 50)],
        (grid, seed, p, ctx) =>
        {
            int n = grid.N;
            double[] z = new double[grid.Cells];
            for (int c = 0; c < z.Length; c++)
            {
                z[c] = Hashing.HashUnit(seed, c, Stream);
            }
            for (int k = 0; k < p.I("smooth"); k++)
            {
                double[] s = new double[z.Length];
                for (int j = 0; j < n; j++)
                {
                    for (int i = 0; i < n; i++)
                    {
                        s[(j * n) + i] = 0.25 * (z[(((j + 1) % n) * n) + i] + z[(((j + n - 1) % n) * n) + i]
                            + z[(j * n) + ((i + 1) % n)] + z[(j * n) + ((i + n - 1) % n)]);
                    }
                }
                z = s;
                ctx.Snapshot($"{k + 1}번 평균", z, note: "이웃 평균을 한 번 더 한 지형"); // 과정 기록
            }
            return new MethodOutput(CompareGrid.NormalizeRelief(z, grid.ReliefM));
        });
}
```

지켜야 할 약속은 네 가지입니다.

1. **꼴.** `Generate(grid, seed, params, ctx) → MethodOutput(z)` 이고, `z` 는 행 우선 (n·n,) 유한한 높이 [m] 입니다(0번 행이 북쪽). 덧붙인 지도는 `output.Layers`, 진단값은 `output.Info` 에 넣습니다.
2. **결정성.** 무작위 값은 `Hashing.Hash3`·`HashUnit` 같은 정수 해시로 만듭니다(`System.Random` 금지). 칸마다 독립인 일만 `Parallelism.For` 로 나눕니다. 같은 입력이면 같은 출력이어야 합니다(시험이 모든 등록 방법을 돌려 확인).
3. **과정 기록.** `ctx.Snapshot(이름, 배열, kind, note, unit, scale)` 로 중간 지도를 남깁니다.
   - kind: `height` 고도, `field` 값, `log` 로그 값, `diverging` 증감, `mask` 표시(고도 위), `category` 종류
   - scale: `self` 는 이 지도의 범위, `final` 은 최종 고도의 범위(고도 단계를 같은 색으로 볼 때)
   - `ctx.Trace(이름, x, y, …)` 는 반복 곡선, `ctx.Bar(이름, [(항목, 값)], …)` 은 막대입니다.
   - 기록만을 위한 추가 계산은 `using (ctx.Extra()) { … }` 안에 두면 생성 시간에서 빠집니다. `ctx.Recording` 이 거짓이면 기록 함수는 아무것도 하지 않습니다.
   - 기록을 켜도 고도가 바뀌면 안 됩니다(시험). 기록 여부에 따라 실수 더하는 순서가 바뀌지 않게 합니다(`FaultingMethod` 의 고정 끊는 점 참고).
4. **시험.** `dotnet test --solution Bpcg.slnx` 가 새 방법도 자동으로 결정성·시드 반영·기록 불변을 검사합니다(`CompareToolTests`).

**새 지표**는 `src/Bpcg/Compare/CompareMetrics.cs` 의 `All` 에 `new("이름", "표시 이름", "단위", "묶음", "설명", 함수)` 를 더합니다. 함수는 고도, 채운 고도, 수신 칸, 상류 면적, 경사 격자, 하천 칸을 담은 `Analysis` 를 받습니다. 잴 수 없으면 NaN 을 돌려주면 표에 '-' 로 나옵니다.

## 5. 화면 (스튜디오 → 방법 비교)

`uv run bpcg studio` 를 켜고 위 막대의 '방법 비교'(`/compare`)를 엽니다.

| 부분 | 하는 일 |
|---|---|
| 위 막대 | 비교 묶음 고르기, 격자 크기 |
| 왼쪽 '시드 묶음' | 시드마다 모든 방법(계열 색 점, 생성 시간). 누르면 가운데에 그 결과 |
| 고도 | 고도 그림 **한 장**. 색 범위를 '이 지형' 또는 '같은 시드 묶음'으로. ◀▶ 같은 시드의 다른 방법, ▲▼ 같은 방법의 다른 시드 |
| 지표 | 그 시드 묶음의 모든 방법 × 지표 표. 머리글에 마우스를 올리면 뜻, 줄을 누르면 그 방법 |
| 연산 과정 | 단계 칩·슬라이더로 중간 지도를 한 장씩(종류별 범례와 설명), 아래에 반복 곡선과 단계별 막대 |
| 왼쪽 '비교 실행' | 설정·묶음 이름·시드·인스턴스·격자를 정해 `bpcg compare run` 을 돌림(먼저 C# 콘솔 빌드). 진행 막대와 기록 |

키보드는 ←/→ 방법, ↑/↓ 시드, [ / ] 과정 단계입니다.

그림은 한 번에 한 장만 그립니다.
- 서버는 잠금 안에서 `bpcg compare render` 를 한 번에 하나씩 부릅니다.
- 한 번 받은 그림 경로는 기억합니다. 파일이 고도·단계 파일보다 새것이면 콘솔을 다시 부르지 않습니다.
- 화면은 요청을 줄 세웁니다. 그리는 중에 다른 것을 누르면 마지막 요청만 이어서 그립니다.

방법별 연산 과정은 다음과 같습니다.

| 방법 | 단계 | 곡선·막대 |
|---|---|---|
| 노이즈 계열 | 처음 1, 2, 3, 4, 6층… 까지 더한 지형(최종 높이 축) | 층별 진폭과 파장 |
| warped | 비틀기 전 fBm, 좌표를 옮긴 거리, 결과 | — |
| diamond_square | 나누기 단계마다 채운 격자점 | 단계별 변위 크기 |
| faulting | 단층 1, 3, 10, 30, 100, 300… 개 | 단층별 변위 크기 |
| thermal | 시작 → 1, 5, 15, 30, 60번 반복 → 높이 변화 | 반복마다 옮긴 칸 수 |
| hydraulic | 시작 → 물방울 1/64·1/16·1/4·1/2·전부 → 높이 변화 | 깎은·쌓은 부피 누적 |
| stream_power | 융기 지도, 처음 지형, 1/16·1/8·1/4·1/2 시점, 최종, 상류 면적 | 최대 변화율, 평균·최고 고도 |
| quilting | 예제, 패치 줄마다, 완성, 붙인 패치 지도 | 패치별 겹침 오차 |
| bpcg | 융기 → 미리 푼 지표 → 깎인 두께 → 거친 격자 시작 → 솔버 결과 → 유량 → 드러난 암석 → 선상지 → 강·호수 → 흙 → 지하수면 깊이 → 동굴 층 | 솔버 반복마다 방향 바뀐 칸·최대 고도 변화·고정 칸, 단계별 시간 |

`bpcg` 의 중간 지도 둘(미리 푼 지표, 거친 격자 시작)은 `Flat.FlatHero` 의 `capture` 갈고리로 받습니다. 갈고리를 주지 않으면 히어로 계산은 그대로입니다.

## 6. 지표

| 지표 | 뜻 | 읽을 때 주의 |
|---|---|---|
| 기복, 고도 적분, 평균 경사, 경사 90% | 지형 모양 | 절차적 방법은 기복을 `relief_m` 으로 맞춘 값 |
| 스펙트럼 기울기 β | 큰 무늬와 작은 무늬의 세기 비 | 단일 프랙탈은 크기와 상관없이 같은 β |
| 웅덩이 점, 웅덩이 넓이·평균 깊이 | 물이 갇히는 곳 (Galin 2019 6.2 의 물길 일관성 검사) | B-PCG·stream_power 는 구조상 0 에 가까움(요구 조건) |
| 하천 밀도 | 상류 0.5 km² 이상 물길 길이 / 넓이 | 문턱에 따라 달라짐 |
| 오목도 θ, 경사-면적 R² | 강이 하류로 갈수록 완만해지는 규칙 | B-PCG(0.45)·stream_power(m/n = 0.5)는 입력이 나오는 값이라 지구다움의 근거가 아님 |
| Hack 지수 | 본류 길이 ∝ 면적^h | 무작위 물길망에서도 비슷하게 나올 수 있음 |

모든 지표의 정의는 `src/Bpcg/Compare/CompareMetrics.cs` 에 있습니다. 어느 지표가 노이즈와 실제 지형을 가르는지는 따로 확인해야 합니다. 이 화면이 그 확인을 위한 도구입니다.

## 7. 한계

- **평면 한 장.** 비교는 12.8 km 평면 한 장의 고도입니다. 행성 전체, 면 경계, 땅속의 일관성은 이 도구로 비교하지 않습니다.
- **B-PCG 쪽 조건.** 융기 단면과 출구를 고정한 평면 히어로라, 시드는 노드 흔들기와 지질 노이즈만 바꿉니다. 노이즈 방법보다 시드 사이 차이가 작은 것은 이 때문입니다.
- **예제 지형.** `quilting` 의 가봉 로페 예제는 레이더 표면 높이(숲 지붕 포함)이고 기복이 약 540 m 입니다. 다른 .npz(키 `z`, `dx`)를 `exemplar` 에 줄 수 있습니다.
- **기존 방법의 구현.** 기존 방법은 논문 식과 널리 쓰는 구현 꼴을 따라 이 저장소에서 다시 짠 것입니다. 원 저자의 구현이 아니므로 매개변수에 따라 결과가 달라질 수 있습니다. 매개변수는 모두 설정에서 바꿀 수 있습니다.
- **시간.** 시간은 이 노트북의 C# CPU 구현(병렬) 시간이라, 논문에 보고된 GPU 구현 시간과 직접 비교하지 않습니다.
- **캐시 무효화.** 코드 판이 어셈블리 전체의 모듈 ID 라, 비교와 상관없는 라이브러리 수정에도 다시 만듭니다. 기본 설정은 다시 만들어도 약 12 초입니다.
